# workerd 应用机制 · 技术路线沉淀

> 来源:Workbench 0.5.0 → 0.8.0 的探索(2026-08-27 ~ 08-28)
> 用途:本产品收敛为「活动栏小组件 + 宿主 SQL API」后,这套机制移交下一个产品继续迭代
> 结论先行:**「AI 造应用」的完整技术路径已经跑通并实测通过;唯一没解决的是宿主 UI 能力的挂载方式无关化(见第 6 节坑 F)**

---

## 0. 一句话概括

让 AI 造出的软件成为**真正的软件**,而不是聊天框里的代码块 —— 路径是:

**应用 = 文件系统里的一个目录 = 一个标准 Cloudflare Worker 网站**,
跑在嵌入的 workerd 里,资源以 binding 注入,写出目录即完成安装,删目录即卸载。

这条路的价值不在「能跑」,而在**它与 Cloudflare 平台同构** —— 本地写的应用代码
能原样部署到云端 D1 + Workers,本地开发与 7×24 云端运行之间没有翻译层。

---

## 1. 演进路线:每一步在验证什么假设

| 版本 | 形态 | 验证的假设 | 结果 |
|---|---|---|---|
| 0.5.0 | 面板体系 | 界面可扩展 | 成立,但只是壳 |
| 0.6.0 | 应用契约 v1(manifest + 前端 + 宿主原语) | 用户/AI 能自造应用 | 成立;**但「不做应用自写后端」这条判断很快被证伪** |
| 0.6.1 | 应用桥换 Cap'n Web,workerd 前置 | 双向对象能力 RPC 可行 | 成立 |
| 0.7.0 | workerd 进舱,AI 可写 `server.js` | AI 写的后端能被安全隔离 | 成立(isolate + 物理断网 + 能力网关) |
| 0.8.0 | **应用即网站**:workerd 成为应用全栈 | 静态资源与 API 都由应用自己应答 | 成立,workerd 使用率 10% → 100% |
| 0.8.0+ | **每应用一个 origin** | 「同源绝对路径」承诺能否兑现 | **必须外置到 workerd 之外才成立**(第 6 节坑 A) |

**关键转折**:0.6.0 明确写下「应用自写服务端代码明确不做,storage+db+fs+agent 覆盖个人应用绝大多数需求」。
一个版本之后就推翻了 —— 因为宿主原语再多也是**宿主定义的领域**,而 AI 造应用的前提恰恰是
「宿主不知道『书签』是什么」。给后端才是把领域定义权真正交出去。

> 这条弯路本身是结论:**原语 API 与自写后端不是量的差别,是权力归属的差别。**
> 如果下一个产品的目标是「AI 造出的东西属于用户」,那就必须给后端;
> 如果目标是「让用户少写点代码」,原语 API 就够了 —— 这也正是本产品收敛的方向,见第 9 节。

## 2. 最终形态:应用 = 目录 = 网站

```
<应用的家>/apps/<id>/
  app.json     manifest:挂载点(路由路径)+ 能力声明
  server.js    Worker:export default { async fetch(req, env) {…} }
  public/      静态资源(env.ASSETS 读这里)
  data.db      数据(env.DB 落这里 —— 和代码做邻居)
```

```json
{ "id": "notebook", "name": "笔记本", "icon": "📔",
  "mounts": { "tab": "/", "panel": "/panel.html" },
  "capabilities": ["db", "ai"] }
```

- **安装 = 目录存在**(扫描自动注册);**卸载 = 删目录**。AI 用 write 工具即可造应用,不装依赖、不起 dev server。
- **挂载点是路由路径,不是文件名** —— 这一条很重要:应用是网站,不是一堆页面文件。
- 预装应用随包发,首次启动复制进「应用的家」,之后与用户自造的应用**无差别**(可改可删)。

### 应用后端长这样(一个完整应用的全部后端代码)

```js
export default {
  async fetch(req, env) {
    const url = new URL(req.url);
    if (url.pathname === "/api/notes") {
      const { results } = await env.DB.prepare("SELECT * FROM notes ORDER BY id DESC").all();
      return Response.json(results);
    }
    return env.ASSETS.fetch(req);   // 其余交给静态资源
  },
};
```

## 3. 架构主轴:workerd 只负责计算,一切资源是 binding

这是从 Cloudflare 平台抄来的形态,不是比喻,是同一套写法:

| binding | 本地实现 | 上云对应 |
|---|---|---|
| `env.DB` | `apps/<id>/data.db`,Node 管的 SQLite | **D1**(接口一致,应用代码一行不改) |
| `env.ASSETS` | `apps/<id>/public/` | Workers Assets |
| `env.HOST` | 宿主专有能力(ai / agent / log) | 无,上云时降级 |

- `env.DB` 是**在 isolate 里现写的 D1 垫片**:`prepare(sql).bind(…).all()/.first()/.run()/.raw()`、
  `exec(建表脚本)`、`batch([…])`(一个事务)。每次调用回环到 Node 执行真 SQLite。
- `env.ASSETS.fetch(req)` 读 public/,未命中且路径不像文件名时回落 `index.html`(SPA 兜底)。
- `env.HOST` 是 `WorkerEntrypoint` 子类 `HostGate`,**能力在此把关**,动作全部经 `env.NODE`
  (external service binding)回 Node 执行。

### 装载:全按需,按内容哈希做版本键

```js
const { code, capabilities, version } = await (await env.NODE.fetch(`/api/apps/server-code?id=${appId}`)).json();
return env.LOADER.get(`${appId}@${version}`, () => ({
  compatibilityDate: "2026-02-01",
  mainModule: "entry.js",
  modules: {
    "entry.js":      ENTRY_MODULE,    // 包装 env 后转交应用的 default export
    "wb-runtime.js": RUNTIME_MODULE,  // D1 / ASSETS 垫片
    "app-server.js": code,            // 应用自己的 server.js
  },
  env: { __WB_HOST: ctx.exports.HostGate({ props: { appId, caps: capabilities } }) },
  globalOutbound: null,               // 物理断网
}));
```

`version` = `server.js` 的内容哈希 → **改完代码下次请求即新 isolate**,旧的自然凋亡。
没有「重启应用」这个动作,也不需要。

## 4. 寻址模型(整套机制里最反直觉的一段)

**workerd 对外只有一个端口**,不管里面跑了多少个应用 isolate。

原因在 workerd 的配置模型:`sockets` 是**静态声明**的,一个 socket 绑一个端口、指向一个**具名 service**:

```capnp
sockets = [ ( name = "http", address = "127.0.0.1:<port>", http = (), service = "overseer" ) ]
```

而动态装载的应用**没有名字**(它是运行时按 `appId@版本哈希` 生出来的),
所以不可能给它配 socket。isolate 根本不是网络端点 —— overseer 调它用的
`worker.getEntrypoint().fetch(req)` 长得像网络请求,其实是**进程内直接调用**,不走 TCP。

于是三层寻址,每层的「地址」形态完全不同:

| 层 | 地址是什么 | 谁解析 |
|---|---|---|
| 到 workerd | TCP 端口 | 内核 |
| 到应用 | URL 路径里的 `token` → `appId` | overseer(问 Node 换算) |
| 到 isolate | 字符串键 `appId@版本哈希` | `LOADER` 的缓存 |

**推论(下一个产品直接拿走):origin 这一层只能在 workerd 外面做,因为 workerd 里面
根本没有「端口」这个东西可以分给应用。** 这一条直接决定了第 6 节坑 A 的解法。

## 5. 安全模型

1. **物理断网**:`globalOutbound: null` —— 应用后端连 `fetch()` 外网都没有,只能经三个 binding 碰外界。
   这是「AI 写的代码可以随便跑」的地基:它想外传数据也没有通道。
2. **能力网关**:manifest 没声明的能力,`env.HOST` 与宿主桥两侧都拒。声明是**明文写在
   app.json 里的**,用户能看见 —— 能力即知情同意。
3. **每应用一个 token**:每次启动随机生成,只绑一个 appId。应用能看见自己 URL 里的 token,
   所以 token 必须猜不出别人的(写死 `/app/todo/` 就完蛋)。
4. **origin 隔离**:见第 6 节坑 A —— 最终由「每应用一个端口」提供,取代了原来的 opaque origin。
5. **AI 行为可问责**:`env.HOST.ai()` / `agent()` 的 `summary` 字段**必填**,每次调用落活动流水。
   机器行为进活动流,不进会话 —— 会话只属于用户亲自开启的对话。

## 6. 六个坑(这份文档最值钱的部分)

### 坑 A ★ 路径前缀 vs 根绝对路径 —— 「同源」承诺是假的

**现象**:应用从面板打开没有样式、数据全空;同一份代码用浏览器直连开发端口一切正常。

**根因**:所有应用挤在一个 workerd 端口上,靠路径前缀 `/app/<token>/` 区分。
但契约承诺「前端与自己的后端同源,直接 `fetch("/api/…")`」——
浏览器会把 `/style.css`、`/api/todos` 解析到 **origin 根**,绕过前缀,直接 404。
**三个预装应用自己全部中招**,只有首页能出(那是 iframe 的 src 本身)。

**为什么没被更早发现**:实测是用 `curl` 打全路径过的,全绿。
> **教训:凡是涉及 URL 解析的机制,curl 测不出来 —— 必须过浏览器。**
> curl 验证的是服务端,浏览器验证的是**契约**。

**走过的错路**:在 overseer 里给 HTML 响应注入垫片 ——
`<base href>` + 重写 `href="/…"`/`src="/…"` 属性 + patch `fetch`/`XHR`/`EventSource`。
能跑,但边界一堆(CSS 里的 `url(/…)`、`el.src = "/…"` 都漏),而且**它在替契约撒谎**。

**正解**:给每个应用一个**真 origin**。做法是 Node 侧为每应用开一个 loopback 端口,
反向代理到 workerd 并补上前缀:

```
浏览器 ──► Node:<appPort>/style.css ──► workerd:<wdPort>/app/<token>/style.css
        (应用的专属 origin)        (前缀退回 Workbench 内部)
```

应用自己看到的永远是根路径,绝对路径天然成立,**注入垫片整段删除**。
成本:一跳 loopback 转发(可忽略)+ 每应用一个端口。

**副产品(白拿的)**:不同端口 = 不同 origin → localStorage / cookie 天然互不可见。
原来坚持 `sandbox="allow-scripts"`(不给 same-origin)的唯一理由就是「同端口会互读」,
这个理由随之消失,iframe 可以给真 origin 了。

> **一条通用结论:当一个隔离手段(opaque origin)是在补偿另一个设计缺陷(共享端口)时,
> 修掉缺陷比加固补偿更划算 —— 而且往往两个问题一起消失。**

### 坑 B ★ 数据落在哪:workerd 的 DO 存储不能用

Durable Object 的存储按 DO id **哈希命名文件**,AI 和用户都摸不到。
而「AI 能管理自己造的应用」是硬需求 —— 它得能 `sqlite3 apps/todo/data.db` 查 schema、改数据。

**结论:数据必须落在应用目录里,和代码做邻居。** 用 Node 管的 SQLite,以 D1 接口暴露。
这同时解决了「上云换真 D1,代码一行不改」。

### 坑 C 服务端 → 客户端的旁路推送做不到

同一条 HTTP 请求内可用(流式响应 / SSE);**回调随调用下传也可用**(实测穿透两跳)。
但后端主动找**别的连接**推事件不行 —— 普通 worker 里 workerd 会判定跨请求上下文并取消。

要旁路推送与定时唤醒(alarms),**必须把会话搬进 Durable Object**。
0.7.0 一度实现了 subscribers/publish,发现走不通后**主动删掉** ——
留着会诱导 AI 写出必然被取消的代码。

> **教训:走不通的 API 不要留半成品,它对 AI 是陷阱。**

### 坑 D 预装应用落地位置 —— 别往用户地盘里塞东西

原实现把预装应用落地到「第一个工作区」。用户把桌面加成工作区,桌面上就凭空多出
一个 `apps/` 文件夹装着三个应用。

**结论:应用要有固定的家**(产品自己的默认工作区根),扫描范围可以覆盖所有工作区,
但**写入只能写自己家**。

### 坑 E 递归文件监听 × 无差别刷新 = 界面抖动

`fs.watch(root, {recursive:true})` + 400ms 节流广播 `tree_changed`,
前端收到就给**所有打开的文件标签**刷新 key → HTML 预览 iframe 整个重挂载。
用户把桌面/家目录加成工作区时,任何进程写盘都会导致预览闪烁。

**结论:变更事件必须带「谁变了」,消费端按 id 精确刷新。** 广播式失效在大目录下必然翻车。

### 坑 F ★ 宿主 UI 能力被挂载方式绑架(唯一未解决的问题)

`workbench.ui.toast` / `tabs.open` / `fs` 这套宿主能力走的是 **iframe → 父窗口的 postMessage 桥**。
一旦把应用改成「浏览器标签打开」(它本来就是个网站,这是最自然的形态),
就没有父窗口,这些 API 全部失效。

**这是设计缺陷,不是实现问题**:宿主能力的可达性**不应该取决于应用被挂在哪**。

**下一个产品必须一开始就避开**。两条候选路:
- **HTTP 回调**:宿主能力也做成 `env.HOST` 的一部分或一个带 token 的本地 HTTP 端点,
  应用无论在 iframe、浏览器标签、还是外部浏览器里都一样可用。代价:UI 类能力
  (toast / 开标签)需要一条服务端→客户端通道(受坑 C 限制,要么走 WS 到宿主、要么轮询)。
- **preload 注入**:如果挂载方式收敛到 Electron webview,用 preload 注入桥。
  简单,但把应用锁死在自家壳里 —— 与「它就是个网站」的定位矛盾。

> 推荐前者:**宿主能力应当是「应用后端能调用的一个能力」,而不是「应用前端能调用的一个宿主对象」。**
> 前者与挂载方式正交,后者永远被 DOM 拓扑绑架。

## 7. 数据产权(这套模型的思想内核)

| 数据 | 归属 | 机制 |
|---|---|---|
| **领域数据**(书签/笔记/日程…) | 应用 | 自己的 `data.db`,自建 schema;**宿主不提供任何域 API,不知道「书签」是什么** |
| **产品本体数据**(会话/文件树/标签页) | 宿主 | 只经能力网关按需开缝 |
| **真实文件** | 用户 | `fs:workspace`,授权制 |

第一行是「AI 能无限造应用」的前提:宿主一旦定义领域,就成了瓶颈,
AI 只能造宿主想得到的东西。

## 8. 成本账

- workerd 二进制 **136MB**,打包后应用体积 **565MB**。每个平台各需一份二进制。
- 0.7.0 时 workerd 只服务「有后端的应用」,使用率约 10% —— 175MB 换一个偶尔用的功能,不划算。
- 0.8.0 让它成为**每个应用的全栈**(静态资源也走它),使用率 100%,这笔地价才付得值。

> **判断标准:嵌入一个重运行时,必须让它成为唯一主干,不能是可选分支。**
> 如果下一个产品里 workerd 只服务一部分场景,那就不该嵌它。

## 9. 与本产品收敛方向的对照(什么时候该回到 worker 模型)

本产品收敛为:**只在活动栏提供小组件;宿主给 SQL API,前端写 SQL 搞定 90% 需求。**
这是正确的轻量化 —— 前提是清楚它的边界在哪。

**这套轻量模型的隐含约束**:
1. 应用只有前端,逻辑全在浏览器里 → 秘密无法持有(API key 只能宿主代持)。
2. 领域由**宿主的 SQL 表结构 + 原语集合**定义 → 宿主是瓶颈;AI 造的东西受限于宿主想到的原语。
3. 没有服务端,就没有:定时任务、后台处理、对外集成、多用户共享状态。
4. 数据在宿主库里 → 应用不可整体搬走,「属于用户」只到数据层,不到软件层。

**撞墙信号(出现两条以上就该升级到 worker 模型)**:
- 反复出现「这个功能得让宿主加个 API」;
- 用户开始要「定时/后台/自动跑」;
- 应用需要持有凭据去访问外部服务;
- 用户想把某个应用**带走**(部署到别处继续用)。

**两条路可以共存**:小组件是「宿主定义领域、AI 填空」;worker 应用是「AI 定义领域、宿主只给算力」。
后者是 AIOS 的完全形态,前者是它的轻量投影。

## 10. 给下一个产品的技术路线

### 直接抄(已验证,别重新发明)
1. **应用 = 目录 = Worker 网站**,manifest 里挂载点是路由路径;写目录即安装。
2. **资源即 binding**,且**接口对齐 Cloudflare**(D1 / Assets)—— 这是本地与云端不分叉的唯一办法。
3. **按需装载 + 内容哈希做版本键**,没有「重启应用」这个概念。
4. **物理断网 + 能力网关 + 能力明文声明**,这是让 AI 随便写后端的地基。
5. **数据落应用目录**,不用 DO 存储(坑 B)。
6. **AI 调用必带 summary,落活动流水**,机器行为与人类对话分流。

### 一开始就要改(踩过的坑)
1. **每应用一个真 origin**,别用路径前缀(坑 A)。端口或子域名都行,但必须是真 origin。
2. **宿主能力设计成挂载无关**,走应用后端而不是前端 DOM 桥(坑 F)。
3. **变更事件带 id,消费端精确刷新**(坑 E)。
4. **产品自己的写入只写自己家**(坑 D)。
5. **走不通的能力直接删干净**,不留半成品(坑 C)。
6. **让 AI 知道产品自身的形态** —— 见下一条,这是整套机制能否被用起来的开关。

### 最容易被忽略的一条:AI 不知道就等于不存在
机制做完之后发现,内部 agent **完全不会用它** —— 因为 system prompt 里
一个字都没提产品自身:它不知道自己跑在什么东西里,不知道有「应用」这个形态,
不知道 workerd 的存在。它只会退化成「我起个 dev server 给你看」。

> **结论:面向 AI 的产品,「机制」和「AI 知道这个机制」是两件独立的工程,后者必须显式做。**
> 具体做法:把应用契约写进 system prompt(形态 + 最小可抄示例 + 硬边界 + 什么时候不该用),
> 并把完整契约文档的绝对路径给它,让它动手前先读。契约文档要**一份三用**:
> manifest 词汇表 = 能力清单 = SDK 文档 —— 三份会漂移,一份不会。

### 仍然开放的问题
1. **旁路推送与 alarms**:需要把会话搬进 Durable Object,未验证(坑 C)。
2. **宿主 UI 能力的挂载无关化**:方案已定,未实现(坑 F)。
3. **多平台**:Windows / Linux 各需一份 workerd 二进制,未做。
4. **应用间通信**:目前物理隔离,没有设计;真要做,应该经宿主而不是让应用互相发现。
5. **应用带走 / 部署上云**:接口已经对齐 D1,但「一键部署」的路径没走过。

## 附录 A:关键文件(Workbench 仓库,供下一个产品对照)

| 文件 | 作用 |

## 附录 B:可复用的验证清单

做这类机制时,下面每一条都要**过浏览器**验证,不能只用 curl:

- [ ] 应用首页能开
- [ ] `<link href="/x.css">` 这类**根绝对路径**的静态资源能加载 ← 坑 A 就死在这
- [ ] `fetch("/api/…")` 能通
- [ ] 深层路由(`/a/b/c`)下相对路径与绝对路径都正确
- [ ] 应用 A 拿不到应用 B 的数据(token 错 → 403;localStorage 互不可见)
- [ ] 后端断网确认(应用里 `fetch("https://example.com")` 必须失败)
- [ ] 未声明的能力被拒
- [ ] 改 `server.js` 后下次请求即新版
- [ ] 删目录后应用消失,端口/数据库句柄被回收
- [ ] **让内部 AI 从零造一个应用并跑通** ← 这是真正的验收,不是开发者自己写一个
